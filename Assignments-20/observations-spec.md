### What this new agent does

It combines the strengths of both your existing agents:

                         User Question

### 1. Multiple document formats

The ingestion layer supports:

* PDF
* CSV
* JSON
* Excel
* Word
* TXT / Markdown

They are normalized into a common `Record` structure.

So your question-answering logic doesn't need to know whether the source came from PDF or Excel.

### 2. LLM becomes a query planner

Instead of asking the LLM:

> "Look at these 8 chunks and tell me the answer."

the new architecture asks it to convert the question into a generic query plan.

For example:

> **Show me all 18K gold products under ₹1 lakh**

Conceptually becomes:

```json
{
  "operation": "filter",
  "conditions": [
    {
      "field": "material",
      "operator": "contains",
      "value": "18K Gold"
    },
    {
      "field": "price",
      "operator": "lte",
      "value": 100000
    }
  ],
  "output_fields": ["name", "price", "stock"]
}
```

Then **Python executes that query**.

The LLM isn't deciding which products qualify.

### 3. No need for a new `if` for every English sentence

This is the important part.

You don't need:

```python
if "18K" in question:
if "22K" in question:
if "under" in question:
if "cheapest" in question:
if "heaviest" in question:
if "available" in question:
...
```

Instead, the LLM maps different ways of asking the same thing into the generic query structure.

The deterministic engine handles:

* equals
* contains
* greater than
* greater than/equal
* less than
* less than/equal
* sorting
* limits
* filtering
* aggregation

### 4. Follow-up questions

It maintains the selected record IDs.

So:

> Show me all 18K gold products.

followed by:

> Show me their prices.

can resolve **"their"** to the products selected in the previous query.

The prices are then retrieved directly from the records—not generated by the LLM.

### 5. Unstructured documents still work

This is where it differs from `ornativa_chatbot.py`.

Suppose you upload a document containing:

> "Customers can return eligible jewellery within 30 days..."

There may not be a nice `ProductRecord` for that.

The agent can route that question to semantic retrieval instead.

So you aren't forced to manually define a schema for every type of document.

### And this reveals something deeper about our new agent

The architecture is correct, but we need to be careful about **follow-up query semantics**.

The conversation is:

```text
Q1: show me all the 18K gold products
    ↓
Result set:
[R1, B402, P501, R101, N201]

Q2: show me the price details of these products
    ↓
"these products" = previous result set
"price details" = requested field = PRICE
    ↓
Retrieve PRICE from those exact records
```

The agent should **never ask the LLM to reconstruct the price from text** at this point.

It should essentially execute:

```python
for product in previous_results:
    return {
        "name": product.name,
        "price": product.price,
        "stock": product.stock
    }
```

Then the LLM can optionally format the result, but **cannot change the values**.

This is exactly the kind of issue that our hybrid architecture is intended to prevent.
